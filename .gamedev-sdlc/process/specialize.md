# Как специализировать канон под проект

`<sdlc-root>/process` задаёт процесс. Репозиторий добавляет факты:
какие домены есть, какие классы включены, какие команды гонять,
чего агент не делает, как устроен GitHub.

Не копировать принципы, роли и рецепты сюда. Ссылка на
`<sdlc-root>/process/...`.

## Конфликт слоёв

1. Корневой `AGENTS.md` потребителя побеждает в объявленных hard invariants.
2. Проектный `<domain>/AGENTS.md` побеждает в путях, именах и локальных
   инвариантах.
3. `<sdlc-root>/process` побеждает в процессе, пока стадия явно не
   выключена в корневом `AGENTS.md` (класс из router отсутствует
   в списке включённых).
4. `<sdlc-root>/<domain>` побеждает в стиле и раскладке домена, пока
   принцип явно не переопределён в проектном `<domain>/AGENTS.md`.

Путь в документах канона всегда `<sdlc-root>`. Потребитель может
вендорить как `sdlc/`, `vendor/sdlc` и т.п. — это один и тот же корень.
Потребитель не читает `<sdlc-root>/evolve/`, пока не меняет канон.

## Что писать в корневом `AGENTS.md` продукта

Держать коротким. Структура —
[templates/AGENTS.project.md](templates/AGENTS.project.md).

Обязательно:

- ссылки на `<sdlc-root>/process` и на каждый используемый домен;
- список доменов;
- включённые классы задач (остальные считать выключенными);
- команды тестов / playtest / точечной проверки / сборки;
- целевые платформы (PC / mobile / обе) и store-пути;
- GitHub: default branch, required checks, кто approve;
- дополнительные human gates;
- локальные hard invariants, которых нет в каноне;
- команды spot-check.

Не копировать сюда инварианты process и доменные принципы.

## Что не писать

- Пересказ [AGENTS.md](AGENTS.md) и [principles.md](principles.md).
- Роли и эскалация — они в [roles/](roles/analyst.md) и [gates.md](gates.md).
- Имена продуктов, которых в репозитории нет.
- `evolve/`, если проект не контрибьютит в канон.
- Секреты store / signing / API tokens.

## Доменный слой

Каждый используемый домен специализируется своим
`<sdlc-root>/<domain>/specialize.md`. Сегодня:
[../game/specialize.md](../game/specialize.md).

Неизвестный домен — [new-domain.md](new-domain.md).

## GitHub

Скопировать / адаптировать шаблоны из `<sdlc-root>/.github/` в продукт.
Правила учёта — [github.md](github.md). Не дублировать process в
описаниях Issue: ссылка на класс router и на пути артефактов.

## Редактор

Skill/rule продукта указывает на `<sdlc-root>/process` и на
существующие домены. Не на `evolve/`, если агент в продукте
канон не меняет. Не копировать тексты канона в skill.

## Новый репозиторий

Рецепт: [workflows/bootstrap-project.md](workflows/bootstrap-project.md).
Не редактировать `<sdlc-root>` под один продукт.

## Когда расширять канон, а не проект

В `<sdlc-root>` — только то, что верно для *следующего* проекта.
Имена, стенды, команды, исключения — в проект.
Подъём в канон — домен [../evolve/](../evolve/), не «заодно поправим process».
