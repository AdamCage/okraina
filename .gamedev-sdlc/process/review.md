# Ревью (процесс)

Как устроен проход ревьюера. Доменный чеклист (playfeel, платформы, …)
не здесь — в `<sdlc-root>/<domain>/review.md`. Сначала процесс,
потом домен.

Роль: [roles/reviewer.md](roles/reviewer.md).
Класс «только ревью»: [workflows/review-only.md](workflows/review-only.md).
Цикл фичи: шаги 5–6 в [workflows/feature-cycle.md](workflows/feature-cycle.md).

## Контекст

Новый субагент. Вход: `spec.md`, `assumptions.md`, дизайн-пакет если есть,
diff, `test-report.md`, предыдущий `review.md` если это не первый проход,
ссылка на GitHub PR. Не история чата implementer-а.

Ревьюер **не патчит** тот же diff. Замечания — в `review.md` и
в review comments PR.

## Статусы пункта

| Статус | Смысл | Блокирует выход? |
|---|---|---|
| `blocker` | Нарушен контракт, инвариант, гейт или проверка красная | Да |
| `should` | Дыра, которую стоит закрыть в этом цикле; не ломает обещание | Нет после первого прохода, если человек не сказал иначе |
| `nit` | Вкус, стиль без нарушения канона | Нет после первого прохода |

Формат файла — [templates/review.md](templates/review.md).
У каждого пункта: проблема / риск / пробел, приоритет, статус.

## Первый проход

Полный разбор: блокеры, should, ниты. Ниты можно написать —
они не держат выход, если блокеров ноль.

Виды критики в одном проходе (по необходимости):

- дизайн-критика (механика / UX / lore vs спека) — часто после элаборации
  критиком ([roles/critic.md](roles/critic.md));
- code review — diff vs контракт и доменный [../game/review.md](../game/review.md);
- playtest-критика — факты из `test-report.md`, не «мне не зашло» без пути.

## Последующие проходы (итерации 2–5)

Только: открытые пункты прошлого `review.md` и регрессия.
Новый вкус не открывать. Новый блокер — только если его создала
правка или он был пропущен как дыра контракта (не «мне не нравится имя»).

## Выход

`blocker = 0`. Иначе — ещё итерация или эскалация.

После 5 итераций с ненулевыми блокерами — к человеку:
в чём дедлок (два прочтения спеки, неснимаемый риск, нет факта),
не список нитов. В PR — summary дедлока, не новый том нитов.

## Что смотреть всегда

- [ ] Класс задачи совпал с объёмом diff-а (не feature под видом hotfix).
- [ ] Есть контракт, если класс его требует; реализация не шире спеки.
- [ ] Открытых аналитических блокеров нет (или есть accept в `assumptions.md`).
- [ ] Тесты / playtest соответствуют классу; красное не записано как «known».
- [ ] Доменный `review.md` просмотрен, если тронут домен.
- [ ] Канон не скопирован в проектные файлы.
- [ ] Нет секретов (ключи store, provisioning, API tokens).
- [ ] PR связан с Issue; labels отражают класс / платформу.

## Чего не делать

- Не предлагать другой движок / стек без запроса.
- Не закрывать блокеры за implementer-а кодом.
- Не требовать полный playtest-пакет на hotfix.
- Не ревьюить файлы вне diff-а «заодно», кроме явной регрессии.
- Не approve в GitHub при живых `blocker` в `review.md`.
