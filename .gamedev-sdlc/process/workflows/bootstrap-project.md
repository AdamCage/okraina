# bootstrap-project — подключить канон в продукт

Цель: в продукте появляется тонкий корневой `AGENTS.md`, указатели
на `<sdlc-root>` и базовая GitHub-обвязка. Канон не копируется.
Следующая задача читает корень → router → домен.

Не редактировать файлы `<sdlc-root>` под этот продукт.

## Шаги

1. **Найти канон как `<sdlc-root>`.**
   Submodule, subtree или копия каталога. Запомнить фактический путь
   в продукте (`sdlc/`, `vendor/sdlc`, …). В текстах канона всё равно
   писать `<sdlc-root>`. Если канона нет — спросить, как подключать,
   не качать молча.

2. **Прочитать процесс.**
   [`<sdlc-root>/process/AGENTS.md`](../AGENTS.md),
   [`<sdlc-root>/process/specialize.md`](../specialize.md),
   [`<sdlc-root>/process/github.md`](../github.md),
   шаблон [`<sdlc-root>/process/templates/AGENTS.project.md`](../templates/AGENTS.project.md).
   Не читать `evolve/` и не читать все домены.

3. **Спросить у человека только факты** (не принципы). За ход —
   короткий список, без романа:
   - какие домены уже есть в репо (сегодня из канона известен `game`);
   - Godot версия (мажор/минор) и путь к бинарнику; язык GDScript
     (default) или C# (opt-in);
   - целевые платформы: PC, mobile, обе;
   - источники истины (дизайн-доки, API, live-ops README);
   - команды test / playtest / build / deploy;
   - чего агент не делает (прод-store, IAP, чужие контуры);
   - какие классы включить (см. router);
   - нужен ли `release` / store ship в этом репо;
   - GitHub: org/repo, default branch, required checks;
   - дополнительные human gates.
   Неизвестное, без которого нельзя написать обвязку — блокер.

4. **Создать корневой `AGENTS.md` из шаблона.**
   Только ссылки, список доменов, классы, команды, платформы,
   гейты, локальные инварианты, spot-check, GitHub-факты.
   Ни одного скопированного принципа process или game.

5. **Известный домен.**
   Для каждого домена из канона, который в продукте реально есть
   (сегодня: `game`), пройти его `specialize.md`.
   Сейчас: [../../game/specialize.md](../../game/specialize.md).
   Появится `<game-root>/AGENTS.md` из доменного шаблона.

6. **Неизвестный домен.**
   [../new-domain.md](../new-domain.md):
   - однореповые факты → тонкая проектная обвязка;
   - переиспользуемый подход → черновик формы game с пометкой
     «кандидат в канон».
   Не создавать домены в `<sdlc-root>` «впрок».

7. **GitHub-обвязка.**
   Скопировать из `<sdlc-root>/.github/` в продукт:
   issue templates, PR template, labels.yml, workflow stubs.
   Применить labels (`gh label` / UI). Описать branch protection
   человеку (агент не меняет protection без гейта).
   См. [../github.md](../github.md).

8. **Провод editor skill/rule**, если инструмент это умеет.
   Указатели: `<sdlc-root>/process` + существующие домены продукта.
   Не `evolve/`. Не вставлять тексты канона в skill.

9. **Ready check.**
   - Следующая задача: корневой `AGENTS.md` →
     [router.md](router.md) → домен.
   - В проектных файлах нет копий канонных принципов.
   - Ссылки открываются (относительный путь от факта вендоринга).
   - Выключенные классы названы явно или отсутствуют во включённых.
   - Issue можно создать из шаблона с полями класса и платформы.

## Артефакты

Обязателен корневой `AGENTS.md` (и доменные, если шаг 5 сработал),
плюс GitHub templates/labels. Спека продукта не нужна. `release.md` не нужен.

## Чего не делать

- Не форкать канон («у нас process чуть другой — поправим внутри vendor»).
- Не тащить `evolve/` в продуктный skill.
- Не заполнять шаблоны канона фактами продукта
  (шаблоны остаются в `<sdlc-root>` пустыми).
- Не коммитить store/signing secrets «чтобы CI заработал».
