# review-only — разобрать чужой diff

Просят ревью или критику, не работу за автора. Ревьюер не патчит
тот же diff. Новый контекст. Процедура: [../review.md](../review.md).

## Шаги

1. **Подтвердить класс.**
   Если в задаче «поревьюи и поправь» — это не review-only.
   Сказать, что патч делает implementer после `review.md`, либо
   человек явно сменил класс.

2. **Собрать вход.**
   Diff / PR, `spec.md`, `assumptions.md`, дизайн-пакет, `test-report.md`,
   проектный и доменный `AGENTS.md`, доменный `review.md`.
   Нет спеки у класса, который её требует — блокер процесса.

3. **Проход.**
   Сначала блокеры (контракт, инварианты, красные проверки, секреты,
   неверный класс, платформенные дыры). Потом should. Потом ниты.
   Доменный чеклист — вторая пачка, не вместо процесса.
   Дизайн / playtest-критика — по фактам артефактов, не по вкусу чата.

4. **Записать `review.md`.**
   Шаблон [../templates/review.md](../templates/review.md).
   Дублировать ключевые `blocker`/`should` в PR review comments с ID.
   Итерация 1 — полный список. Повторный вызов на том же PR —
   только открытые пункты и регрессия.

5. **Стоп.**
   Не оставлять «я тут чуть подправил». Не force-push. Не merge
   и не approve при живых блокерах, если проект не поручил иное.

6. **Эскалация.**
   Если это уже >5 итераций ревью на одном PR — к человеку с дедлоком,
   не новый том нитов.

## Артефакты

Обязателен `review.md` (+ PR comments). Код ревьюера — нет.

## Чего не делать

- Не менять тон и ревьюить «сам себя» в том же чате implementer-а.
- Не требовать полный feature-набор тестов на hotfix-diff.
- Не предлагать сменить движок без запроса.
